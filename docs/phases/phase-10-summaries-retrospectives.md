# Phase 10 — Summaries, Recurring Symbols & Retrospectives

**Deps:** 09 · **Spec:** FR-20, §6.5, §15.2, §19 · **Outcome:** accumulated history starts paying the
user back on its own — journey narratives, contextual recurring symbols, weekly/monthly retrospectives
and gentle resurfacing, every claim traceable to source objects.

## Scope

**In:** `period_summaries`, `summarize_period`, `journey_narrative`, recurring-symbol analysis v2,
retrospective screens, on-this-day resurfacing, unresolved-question review, journey change detection,
summary compaction feeding retrieval.

**Out:** notification delivery and share cards (11).

## Tasks

### 1. Schema
`period_summaries` per [../DATA_MODEL.md](../DATA_MODEL.md#retrieval--summaries--phases-09-10):
`source_object_ids` is `not null` with a **non-empty check constraint**, plus an application rule that
the set may not consist solely of other summaries or interpretations (§19). RLS enabled.

### 2. Journey narrative header (§6.5)
- `journey_narrative` replaces Phase 07's deterministic header: one concise sentence ("Your readings
  shifted from hesitation to action over the last 3 months") plus progression labels.
- Grounded only in the journey's evidence package; hedged register; source IDs persisted.
- Regenerated when the journey materially changes (new member, confirmed outcome, ≥14 days), never on
  every view (§19: opening never requires an AI call — the stored narrative is served).

### 3. Period summaries (FR-20)
- Weekly and monthly for the user, plus per-journey, generated by a job **only when enough data exists**
  (thresholds: ≥3 objects in the period for weekly, ≥5 for monthly; otherwise nothing is generated and
  nothing is shown — no filler).
- Content: what recurred, what shifted, what remains open, which outcomes were confirmed; each claim
  carrying source IDs. Confirmed facts, inferred events and tarot interpretations are visibly
  distinguished (§9.2).
- Compaction: summaries become retrieval-eligible objects (Phase 09 step 4) so long histories stay
  bounded — but they **augment** evidence, never replace it, and may never be the sole support for a
  real-life claim.
- Dismissible; dismissal remembered; regeneration explicit.

### 4. Recurring symbols v2 (FR-17)
Upgrade Phase 07's section with real context (§3.3 "not merely statistics"):
- Which cards/suits/themes recur, **when**, around which journeys, before or after which confirmed
  events, and whether the user confirmed a connection.
- Rendered as at most one meaningful visual (a sparse timeline of occurrences) plus prose — never a
  chart grid (§4.3).
- Every claim links to its readings. A pattern with fewer than 3 occurrences is not called a pattern.

### 5. Retrospective surfaces (§15.2)
- **Monthly retrospective** screen: recurring card/theme, confirmed life events, outcomes recorded,
  journeys that moved, open loops. Built from user-confirmed data wherever possible.
- **On this day / 30 days ago:** resurfaces one old reading with a revisit prompt — content-anchored,
  at most one per day, easily switched off (§15.2, and no compulsion per §4.7).
- **Unresolved question review:** "you've asked about X three times without resolving" → offers
  reflection and outcome recording, explicitly **instead of** encouraging a new pull (§15.2, §10).
- **Journey change detection:** "your last three readings shifted toward action" — only when the theme
  progression actually changes, and only once per shift.
- Home's "one relevant retrospective insight" slot (Phase 01) now fills from these, showing **at most
  one** thing at a time (§5 Home purpose).

### 6. Demo data
Seed enough density for a real monthly retrospective and at least one detectable journey shift.

## Test plan

- [ ] Unit: threshold logic (no summary below the data floor); recurring-symbol contextualiser (a
      2-occurrence card is not a pattern); change detection fires once per genuine shift.
- [ ] **Invariant `summary-never-sole-evidence.test.ts`** extended: a `period_summaries` row whose
      `source_object_ids` contain only summaries/interpretations is rejected at the application boundary,
      and the empty-set case is rejected by the DB constraint.
- [ ] Provenance: every claim in a generated summary maps to a source ID present at generation time;
      deleting a source scrubs or stales the summary and the UI reflects it (§19).
- [ ] Integration: narrative regenerates on material change only; stored narrative served on view with
      **zero AI calls** (provider spy); dismissals persist.
- [ ] **RLS** on `period_summaries`; B cannot read A's summaries.
- [ ] E2E at 390px on demo data: open a journey and read the narrative header → open the monthly
      retrospective → tap through to sources → see an on-this-day card and dismiss it → turn the
      resurfacing off in Profile and confirm it stops.
- [ ] Anti-compulsion check (manual + test): no streak counters, no badges, at most one resurfacing per
      day, every retention surface dismissible and switchable off (§4.7, §15.2).
- [ ] a11y: retrospective sections are navigable by heading; the one visual has a text equivalent.
- [ ] `pnpm eval`: summary fixtures checked for unsupported claims, correct fact-status attribution and
      hedged register. Unsupported claims block the phase.

Manual:
- [ ] Read the monthly retrospective for the demo user. Would a real user find it worth opening? If it
      reads as generic, the fault is the prompt or the data floor — fix, don't ship filler.

## Exit criteria

- [ ] Journey narratives and period summaries generated only above data floors, stored, source-grounded.
- [ ] Recurring symbols are contextual with evidence links; nothing below 3 occurrences called a pattern.
- [ ] All four retention surfaces live, each dismissible and switch-off-able, max one at a time.
- [ ] Viewing any summary makes zero AI calls.
- [ ] Summary-provenance invariants passing; deletion scrubs summaries.
- [ ] Report + `../PROGRESS.md` updated.
