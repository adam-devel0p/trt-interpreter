## 1. What was built

Accumulated history now pays the user back on its own, and every sentence it offers can be
traced to the entries it rests on. A **journey's header** is a stored one-sentence narrative
with its progression labels and source ids (`journey_narratives`), written by
`journey_narrative` from the same bounded evidence package the Ask answerer gets, verified
(citations, register), regenerated only when the journey materially changes (member set,
confirmed outcomes, or 14 days) and otherwise served as stored — the deterministic counts stay
beneath it, or stand alone when nothing grounded could be written. **Period summaries**
(`period_summaries`) exist for complete weeks and months and for journeys, generated by
`summarize_period` **only above a data floor** (3 / 5 / 5 objects): a headline and four
sections — what kept coming back, what shifted, what is still open, what the user confirmed —
each claim carrying its **basis** (confirmed by you / from the cards / your reflection /
noticed by the app) and its citations as object ids; a "confirmed fact" that cites no
confirmed evidence is dropped before storage, and the source set is non-empty by database
check and never solely generated text by application rule. Summaries are dismissible,
regeneration is an explicit button that says "one model call", a deleted source scrubs and
stales them (job and trigger), and each becomes a retrieval-eligible object that can travel
with an Ask package as compression of entries the bound left out — never as the sole support
of a claim. **Recurring symbols** are contextual: when each appeared (one sparse timeline with
a text equivalent), around which journeys, before or after which confirmed events, whether
the user confirmed a connection, and a symbol is called a *pattern* only from three readings.
The **monthly retrospective** (`/retrospective/YYYY-MM`, weeks too) is built from confirmed
data first and adds the summary when one exists; the index lists thin months without a link.
**Home's one insight** is filled from four retention surfaces — a journey shift (once per
shift), an unresolved-question review (three unresolved readings about one subject, offering
reflection and outcome recording instead of a new pull), the month to look back on, and one
old reading on this day (at most one per calendar day) — one at a time, each dismissible with
the dismissal remembered, each switchable off in Profile. No streaks, counters or badges
anywhere. The demo journal carries seven summaries, three narratives and a detectable shift.

## 2. Decisions made

| Decision | Reasoning | Alternative rejected |
|---|---|---|
| **Summaries reuse the Ask evidence package** (`retrieval/evidence.ts`, ≤ 24 objects / 6000 tokens, date order) rather than a new rendering | One privacy boundary for what a model sees of history (§11); the labels, derived-field marking and link grading already exist; `confirmed` per label is the only addition | A summary-specific prompt input with full notes |
| **Each claim carries a `basis`; a `confirmed_fact` must cite a confirmed label or it is dropped** | §9.2 asks for confirmed facts, inferred events and interpretations to be visibly distinguished; the verifier makes the attribution mechanical and §21.7 holds at the boundary — the model cannot state a fact the user did not record | Trusting the label the model chose; relabelling instead of dropping (the sentence would still read as a fact) |
| **Data floors are hard: below them nothing is generated and the screen says so without a link** | FR-20 "after enough data exists"; a paragraph about one reading is filler (§4.3) | A shorter "thin period" summary |
| **Only complete periods are summarised; the sweep fills missing recent ones; regeneration of an existing summary is the user's explicit action** | The phase file: "dismissible; dismissal remembered; regeneration explicit". A stale summary is marked, not silently rewritten | Regenerating on every new outcome |
| **Narrative regeneration is fingerprint-driven and queued from `refreshJourneys`** (deduped, 120 s) | `refreshJourneys` is already the single hook every live-member change passes through; the runner's fingerprint check makes the job idempotent, so the queue can be noisy without a model call | A view-time freshness check (would violate §19's zero-call rule) |
| **A summary's source set is the cited objects (the whole package when nothing cites)** | The set is what the summary rests on; purge scrubs by it; the DB check keeps it non-empty | The whole package always |
| **Deletion scrubs a summary and marks it stale; the last source deletes it** — by the `summaries_source_cascade` trigger and the purge job's explicit step | §19 "deleting a reading removes or invalidates its summaries" for every delete path; a stale summary is still traceable (every remaining claim keeps ≥ 1 citation; a claim that rested only on the gone entry goes) | Deleting every summary that touched the entry |
| **Covering summaries join the Ask package only for dropped entries, labelled after the objects; `verifyAnswer` drops summary-only claims** | §8.1 step 4 compression without displacing an entry; §19 "never the sole evidence" enforced mechanically, not by prompt | Summaries as search candidates competing with entries in `search_history` |
| **Patterns need three occurrences; two are listed as "twice"** | §3.3 and the phase file; the Phase 07 e2e that expects a two-occurrence card listed on the journey page stays true — the row exists, it is just not called a pattern; the retrospective shows `patterns()` only | Raising `RECURRENCE_MIN` to 3 (would hide honest information) |
| **Home shows a pending journey suggestion before any retention surface** | A suggestion is a decision waiting on the user; retention surfaces are gentler and can wait; "one thing at a time" (§5) either way. A surface is recorded as shown only when it actually takes the slot | Insights first (broke the Phase 07 e2e and buried a pending question) |
| **The four switches live on `reminder_settings`** (default true, row on first change) | The table was built for exactly this (Phase 01) and Phase 11's delivery switches sit beside them | Columns on `profiles` |
| **A session may change only `dismissed_at` on a summary** (`period_summaries_protect` trigger) | §21.4: derived text is derived; the owner reads, dismisses, deletes | An update policy alone (would let a session rewrite the text) |
| **The explicit regenerate actions go through the job queue and run that one job inline** | Keeps the model layer reachable only through the lazy handler registry (`opening-reading-makes-no-ai-call` scans the journey routes); the user still sees the result on return | Calling the generator from the server action |
| **`journeys.summary` stays unused** | The narrative is a versioned artefact with sources and a fingerprint; a text column cannot carry that | Writing the sentence into `journeys.summary` |

## 9. UX notes

The retrospective is a single article of sections, each with a real empty state ("Two
appearances are two appearances, not a pattern"; "No outcomes recorded this period"), the
summary first because §4.2 says conclusion before detail — but with its provenance line
("Written by the app … Not a record of anything") and, when a source was deleted, a plain
notice and the regenerate button. The Home insight card has one eyebrow per kind ("Something
moved", "Worth a look back", "A month to look back on", "On this day, a year ago" / "30 days
ago") and never more than one card. Profile's "Looking back" section names each surface in
the user's terms and says "there are no streaks".

Rough edges left deliberately: the journey page's "Rests on" list can run long for a
narrative citing four questions; the retrospective's "Outcomes you recorded" is by
confirmation date (an outcome recorded later about a reading of the period appears in the
month it was recorded, which is honest but can read as "nothing" for old months — the demo
seed now back-dates outcome confirmations so the demo months have them); regenerate runs
inline and the page refreshes when done, with no progress skeleton; the sparse timeline is
one row per symbol rather than one shared axis.

## 11. Known issues and risks

- **The mock summariser and narrator are English rule scaffolding.** They cite honestly by
  construction; the real prompts have not been run. The eval's `no_unsupported_facts`,
  `no_unknown_labels`, `basis_attribution` and `no_invented_cards` checks are what to read on
  the first real run — the verifier drops what fails, and a summary with nothing left is not
  stored (the screen then says "No summary has been written").
- **The demo's journey shift is real but small** (two entries in the newest step). With the
  real extractor the progression will be richer; `SHIFT_MAX_AGE_DAYS` and the "newest step
  differs" rule are the dials.
- **A summary's evidence is a strict date-order prefix** when a period holds more than 24
  objects: the latest entries of a very busy month are dropped (the prompt is told). A
  sampled package is a small change in `packageEvidence` if it ever matters.
- **`retention_prompts` grows by one row per shown surface** (a few per user per month);
  nothing prunes it. Harmless; a 12 ops item if it ever matters.
- **Two `regenerate` clicks in flight** run two jobs; the second sees the first's hash and
  still regenerates (`force`). One extra call at worst.
- `pnpm eval --dry` rewrites the other tasks' baselines' `ran_at`; reverted as in 09.
